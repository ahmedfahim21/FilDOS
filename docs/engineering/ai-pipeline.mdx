engineering that makes that practical on a personal machine.

## Processes

Heavy or untrusted work never runs in the main process. Each job has its own
Electron **utility process**, a separate main entry in the electron-vite config:

| Worker | Runs | Notes |
|--------|------|-------|
| `modelWorker` | Embeddings (`@huggingface/transformers` on native **onnxruntime-node**, CPU) | Low OS priority, half the cores (max 4); exits after 2 min idle |
| `extractWorker` | Text extraction — pdfjs, mammoth, plain text | Watched: 2 min per read, 1 GB heap cap, restarted on failure |
| `llmWorker` | The assistant LLM (`node-llama-cpp`, Metal on Apple Silicon) | One model resident, one chat at a time |

Audio and video are decoded by Electron's own Chromium in a hidden, sandboxed
view (see [Audio and video](#audio-and-video)), and HEIC photos by the
operating system — so FilDOS ships no ffmpeg and no extra codecs.

Model weights cache under `userData/models`. The main process passes that path
to the worker in an env var, because a utility process can't call `app.getPath`.

## One model for everything

`src/shared/aiModels.ts` holds the catalog. One embedding model indexes every
file: **EmbeddingGemma 2** (`onnx-community/embeddinggemma-2-ONNX`, 768-d)
places text, pictures, video frames and sound in **one vector space**. So a
text query can match a photo, a page, or a moment in a recording, and a single
ranking covers them all.

Its text model, vision encoder and audio encoder are separate downloads. Each
loads only when needed: searching needs only the text model, the vision encoder
loads with the first picture, and the audio encoder downloads with the first
recording.

The model card's rules are enforced in code:

- **Task prefixes** (search query, question, `title: <file name> | text:` for
  passages, none on media) live in one file, `@shared/embeddingPrompts.ts`.
  Changing them bumps `PROMPTS_VERSION`.
- **Never float16.** Weights are `q8` or `fp32`; the model's activations
  overflow fp16. Any NaN, infinite or zero vector throws instead of being
  stored.
- **Matryoshka truncation** goes through one helper that truncates and then
  renormalizes (768/512/256 only).

An **index fingerprint** (model, dtype, dimension, prompts) is stored with the
index. On a mismatch the index is emptied and rebuilt, and superseded model
folders are deleted at startup.

<Note>
  Inside Electron, ONNX Runtime crashes on large or reshaped batches unless its
  CPU memory arena and memory-pattern reuse are off. So the worker runs with
  both off and splits every call to stay under 2,048 tokens. Memory peaks about
  4× lower at the same speed.
</Note>

The chat catalog lives in `src/shared/llmModels.ts` (0.6B–35B, grouped by
family), and users can add any GGUF from Hugging Face at runtime.

## Indexing

```text
extractWorker  →  chunk.ts  →  modelWorker  →  vectorStore.sqlite.ts
(text, pdf pages,  (~512-token   (EmbeddingGemma 2)  (Float32 BLOBs +
 docx)              windows)                          in-memory cache)
```

`indexer.ts` orchestrates it. It crawls the roots and compares `fs.stat`
against per-file `index_state`, so unchanged files cost nothing. Then it drains
a persistent `index_jobs` queue as a two-stage `prepare` → `commit` pipeline,
yielding between files. Notable properties:

- **Hits know their place.** PDFs are read page by page through a byte-range
  transport (book-size files up to 512 MB stay in bounded memory). Chunks never
  span pages and carry their page number. Video frames and audio windows carry
  their time in seconds.
- **Two passes for long files.** The first pass reads the first 50 pages of a
  PDF or 40 passages of a document. Once the queue is empty, a later pass reads
  the rest in steps (30 pages / 40 passages). New jobs interrupt it and go
  first.
- **Cost-classed queue.** Removals and text go first, pictures next, PDF/DOCX
  after that, media last, so a fresh index is useful in minutes.
- **Duty-cycled.** Near full speed when you're away, about half while you're
  active, gentler on battery or when the machine runs hot. You can also limit
  indexing to set hours.
- **Keyword-only where vectors don't help.** Data and config files (CSV, JSON,
  YAML, logs, SQL…) and mostly-numeric text get keyword entries without
  vectors.
- **Never dropped.** A file whose content can't be read (corrupt, encrypted,
  scanned, or a timed-out parse) keeps a humanized-filename entry, so name
  queries still find it.
- **Safe default rules.** Skipped: dotfiles, system folders, `node_modules`,
  caches (including `CACHEDIR.TAG` folders), files holding secrets (`.env`,
  keys, certificates, credentials), and dataset folders (hundreds of
  machine-named media files; never a camera roll). Checked-out codebases are
  indexed docs-only, and build output is never descended.

**Ambient mode** keeps indexing alive after the last window closes: the app
stays in the menu bar or system tray and shows live progress.

### Pictures

Pictures are embedded at a vision budget of 140 tokens (screenshots get 280, for
their small text). HEIC/HEIF photos are HEVC-coded, which neither the model
runtime nor Chromium can decode. On macOS and Windows the operating system
decodes them: FilDOS reads the photo's size and rotation from the HEIF
container, then asks the system thumbnailer for an image at that aspect, at
most 1024 px. Linux has no system decoder, so there HEIC photos are found by
name.

### Audio and video

`src/main/media/decoder.ts` runs a hidden, sandboxed `WebContentsView` in its
own session. Its `fildos-decode://` origin serves only files the main process
issued a one-time token for.

- **Video:** a frame every 3 s (at most 40 per file), one per distinct shot,
  embedded at 70 vision tokens.
- **Sound:** 30 s windows overlapping 5 s, at 16 kHz mono, for audio files and
  video soundtracks alike.
- **Limits:** at most 1 hour per file; the decoder closes after a minute idle.

### Extraction watchdog

`extractClient.ts` is the watchdog around the extraction worker:

- **Time limit:** a read that runs past 2 minutes kills the worker and fails
  that file with `ETIMEDOUT`.
- **Crash or heap cap:** the reads in flight are re-sent once on a fresh
  worker. The file that caused the crash fails on its second try; files that
  only shared the worker with it go through.
- **Idle:** the worker stops after a minute without work.

Chat and "Find similar" read files through the same worker.

### Estimates

Before and during a run, `estimate.ts` predicts how long indexing what's left
will take, per root and per top-level folder, from metadata alone: file counts
by kind, real PDF page counts, media durations. These are multiplied by a cost
table. The table starts from measured seeds and is then replaced by your
machine's own measured costs (recent-weighted, in `prefs.index.costs`).
Progress reports carry an ETA.

## The vector store

Vectors are Float32 BLOBs in SQLite, searched with **brute-force cosine** over an
in-memory cache that holds vectors only, no texts. The cache warms on the first
search, stays coherent through upsert/remove/remap/clear, and is released after
10 idle minutes. There's no ANN index or vector DB: dot products over a
personal-scale index take tens of milliseconds.

## Ranking

`search.ts` scores every chunk against the query and z-normalizes the scores
per modality (text, picture, audio) on the query's own scale. A file qualifies
in one of two ways:

- **On meaning:** its best segment is at least 2 standard deviations above the
  rest, and above the model's minimum cosine.
- **On words:** it holds at least half the query's terms (BM25 via MiniSearch;
  prefixes only for terms no file holds as typed).

The score is `z + 2·coverage^1.5`, plus 1 when the query names a file kind
("a photo of…", "in a video"). Lookups (codes, IDs) qualify by words only.

So an unanswerable query returns **nothing** instead of the nearest noise, and
the result reports how many hits are clear matches. The UI folds the rest under
"weaker matches". Each hit points at its segment: a page, a moment, a marked
snippet, and a passage that chat hands to the model. See
[Search by Meaning](/features/ai-search) for the product view.

## The assistant (LLM)

The "Ask AI" panel is powered by `src/main/ai/llm/`:

- **`llmWorker.ts`** runs `node-llama-cpp` in its own utility process. It
  downloads GGUF weights, keeps one model resident, runs one chat at a time,
  and streams tokens back as `chunk` messages.
- **`context.ts`** builds the prompt from `@file` mentions, `#folder` listings
  and `/`commands. `/find` runs the index search first, embedding the query as a
  question, and passes each hit's page or moment along.
- **Chat tools:** `@shared/chatTools.ts` defines create/copy/move/rename/
  delete/list/read tools with GBNF JSON schemas. The worker function-calls them,
  RPCs each call to main, and main executes it against `fs/service` with
  injected deps. Every action is recoverable: deletes go to the Trash, nothing
  is overwritten.
- **Persistence:** every exchange, including mentions and `/find` sources, is
  saved to `chat_sessions` + `chat_messages`, so conversations resume later.

## The knowledge graph (Canvas)

`src/main/ai/graph/` fuses three signals into a `GraphSnapshot` with Louvain
communities:

- embedding **similarity** (per-file centroids → partitioned kNN; pictures and
  documents link because they share one space)
- **entities** (opt-in on-device NER)
- **temporal sessions** (from mtimes)

`GraphBuilder` is lazy and incremental, runs under the same duty-cycle as the
indexer, and renders through **cosmos.gl** (GPU force layout + WebGL). See
[Canvas](/features/canvas).

## Testing the AI layer

Dependencies (provider, extractor, decoders, pacing) are **injected** into
`Indexer`, `IndexWatcher` and `GraphBuilder`, so tests drive the whole pipeline
with a fake provider and a temp directory, no Electron required. Quality is
measured separately by the eval harness, which runs the real model on a
generated testbed. See [Testing](/engineering/testing).
